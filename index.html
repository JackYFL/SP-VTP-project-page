Abstract

Language instructions specify task semantics but can be ambiguous when several visually similar objects and candidate targets are present. We study whether first-frame spatial prompts can specify which object to manipulate and where to place it as the egocentric viewpoint changes.

We formalize this setting as Spatially Prompted Visual Trajectory Prediction (SP-VTP), an offline trajectory-prediction setting. EgoSPT contains 2,841 fork pick-and-place episodes across three scenes, with first-frame object/target annotations and recovered 3D end-effector motion.

SPOT fuses a fixed first-frame task representation with the current image and recent motion history, without an explicit object tracker. Three-seed experiments show lower translation and endpoint errors with spatial prompts; interventions reveal different roles for object and target cues. Sequential predicted-state replay confirms that prompts reduce, but do not eliminate, accumulated drift. These results do not establish closed-loop robot success or transfer to new objects and tasks.

EgoSPT Dataset

EgoSPT grounds manipulation goals with lightweight first-frame object-target prompts and supervises future 3D end-effector trajectory chunks from egocentric observations.

2,841 egocentric episodes
112,856 original sliding-window samples
3 scenes shared by train and validation

EgoSPT is collected with a modified Universal Manipulation Interface. Each episode contains egocentric video, object and target bounding-box annotations in the initial frame, and recovered end-effector poses. A deterministic scene–task-group split keeps all episodes of a selected task group in one partition. All three scenes appear in both training and validation: the standard benchmark uses 2,584 training episodes and 257 validation episodes (10,024 validation windows). Per-scene results characterize layout complexity, not unseen-scene transfer. The dataset covers one manipulated-object category and one task family: fork pick-and-place.

SPOT Policy

Task Encoder Observation Encoder Trajectory Generator

Task Encoder

Encodes rendered boxes and coordinate tokens on the first frame. The resulting task representation stays fixed throughout the episode; no explicit object tracker is used.

Observation Encoder

Combines the current egocentric frame with the previous four EE states. Standard evaluation uses recorded history; the sequential diagnostic separately feeds back predictions.

Trajectory Generator

Uses flow matching to generate 16 relative EE waypoints with translation, 6D rotation, and gripper width. Each waypoint is relative to the chunk origin, not a per-step motion increment.

What happens when history is predicted?

Sequential state/history feedback with replayed RGB—not a robot rollout.

We reuse the trained checkpoints and fixed first-frame prompt. After one recorded initialization, feedback modes use each 16-step chunk for the next history; the cumulative condition also uses its predicted endpoint as the next pose anchor, without GT resets. All modes still read recorded video frames. Predictions do not change the image, object state, contact, or termination.

Errors accumulate; prompts mitigate but do not eliminate drift. Correct prompts reduce cumulative episode-end FDE by 45.3% and ADE by 27.6% relative to No Prompt. Even then, episode-end S@10 is only 16.86% and Combined@10 is 5.45%. These are offline endpoint criteria, not physical pick-and-place success rates.

Do not compare 4.55 cm with the 11.14 cm benchmark FDE. The former scores the last valid waypoint of each episode, including partial tails; the latter scores every fixed-16-step sliding window. This diagnostic also uses corrected raw-frame alignment and recomputes all paired GT controls. Each of the 36 evaluations covers 986 sequential queries and 13,906 future waypoints. The current predicted pose may become inconsistent with the replayed camera viewpoint, so this is neither a deployment-success measurement nor a guaranteed upper/lower bound.

Protocol, metric definitions, and downloadable results

Queries occur at steps 4, 20, 36, …, using H=16 and K=4. History excludes the current state and is re-expressed at the next chunk anchor. All relative waypoints are composed with their common chunk origin—not chained as incremental transforms. Gripper width remains absolute. Future GT actions are used only for scoring.

The recorded-history/recorded-anchor control is recomputed with the same corrected alignment, episodes, query times, and initial trajectory noise as every other condition. The corrected loader would yield 10,051 complete sliding windows, versus the original 10,024; neither index set defines the sequential schedule. Each evaluation has 746 full chunks and 240 partial tails. First-chunk agreement, paired noise, full tail coverage, and no cumulative GT anchor reset were audited. The regression suite passes 59 tests.

ADE first averages Euclidean position error over all valid future waypoints of an episode, then across episodes. Episode-end FDE uses only its final valid waypoint. End Combined@10 additionally requires endpoint rotation within 20° and matching gripper state (open when width exceeds 3 cm). All endpoint rates are offline agreement criteria, not physical task success.
